
# Обзор архитектуры проекта "Ревьюша"

## 1. Назначение документа

Этот документ описывает высокоуровневую архитектуру системы "Ревьюша":

- основные приложения;
- инфраструктурные компоненты;
- внешние сервисы;
- взаимодействие между компонентами;
- основные пользовательские сценарии.

Документ не описывает детали реализации отдельных модулей.

---

# 2. Общая идея системы

"Ревьюша" — это AI-платформа для автоматического Code Review.

Пользователь загружает исходный код проекта или подключает репозиторий.

Система:

1. Принимает проект.
2. Сохраняет исходные файлы.
3. Запускает асинхронный процесс анализа.
4. Разбирает структуру проекта.
5. Передаёт части кода AI-моделям.
6. Обрабатывает результаты.
7. Формирует итоговый отчёт.
8. Предоставляет пользователю возможность изучить замечания и общаться с AI.

# 4. Основные компоненты системы

## 4.1 Web приложение

Технологии:

- React 19
- Vite
- TypeScript

Ответственность:

- пользовательский интерфейс;
- управление проектами;
- загрузка файлов;
- просмотр прогресса;
- просмотр отчётов;
- AI чат.

Web приложение не имеет прямого доступа к:

- PostgreSQL;
- Redis;
- MinIO;
- AI сервисам.

Все действия проходят через API.

---

## 4.2 Admin приложение

Отдельное React-приложение.

Ответственность:

- управление пользователями;
- просмотр системной статистики;
- контроль очередей;
- просмотр логов;
- управление настройками AI.

Admin использует тот же API, но с повышенными правами.

---

## 4.3 Backend API

Технологии:

- NestJS 11
- Prisma
- PostgreSQL

Ответственность:

- бизнес-логика;
- авторизация;
- управление пользователями;
- управление проектами;
- создание задач анализа;
- работа с отчётами;
- управление правами доступа;
- взаимодействие с очередями.

API не выполняет:

- анализ больших файлов;
- длительные AI запросы;
- генерацию больших отчётов.

---

## 4.4 Worker

Отдельное приложение NestJS.

Ответственность:

- выполнение фоновых задач;
- обработка очередей;
- анализ файлов;
- подготовка данных для AI;
- сохранение результатов.

Worker может масштабироваться независимо от API.

Например:

```
1 API instance

+

10 Worker instances

```

при большом количестве анализов.

---

## 4.5 AI Service

Отдельный слой взаимодействия с языковыми моделями.

Ответственность:

- отправка запросов LLM;
- управление промптами;
- обработка ответов;
- контроль лимитов;
- выбор модели.

AI Service не зависит от конкретного провайдера.

Возможные модели:

- DeepSeek через OmniRoute;
- другие LLM;
- локальные модели.

---

# 5. Инфраструктурные компоненты

## 5.1 PostgreSQL

Основное хранилище структурированных данных.

Хранит:

- пользователей;
- проекты;
- настройки;
- результаты анализа;
- замечания;
- историю действий.

PostgreSQL является источником истины системы.

---

## 5.2 Redis

Используется для временных данных.

Назначение:

- BullMQ;
- кэширование;
- rate limiting;
- временные состояния;
- блокировки.

Redis не хранит критические данные.

---

## 5.3 MinIO

Объектное хранилище.

Хранит:

- ZIP архивы;
- исходный код проектов;
- промежуточные файлы;
- отчёты;
- экспортированные данные.

PostgreSQL хранит только метаданные файлов.

# 7. Синхронные операции

Операции, которые выполняются сразу:

- регистрация;
- вход;
- получение списка проектов;
- просмотр отчётов;
- изменение настроек;
- управление профилем.

---

# 8. Асинхронные операции

Операции через BullMQ:

- загрузка больших проектов;
- распаковка архивов;
- анализ файлов;
- запросы к LLM;
- генерация отчётов;
- экспорт данных.

---

# 9. Принцип взаимодействия компонентов

## Frontend → Backend

Только через REST API.

---

## Backend → Database

Через Prisma.

---

## Backend → Worker

Через BullMQ.

---

## Worker → AI

Через AI Service.

---

## Worker → Storage

Через MinIO API.

---

## Все компоненты

Обмениваются только через определённые интерфейсы.

Прямые зависимости запрещены.

---

# 10. Масштабирование

Архитектура позволяет независимо масштабировать:

## API

При большом количестве пользователей.

---

## Worker

При большом количестве анализов.

---

## AI слой

При большом количестве запросов.

---

## Storage

При росте количества проектов.

# 12. Итоговая модель системы

Ревьюша состоит из четырёх основных приложений:

```
apps/

web
    Пользовательский интерфейс

admin
    Административный интерфейс

api
    Основная бизнес-логика

worker
    Фоновые задачи и AI pipeline
```

и инфраструктуры:

```
PostgreSQL
    Данные

Redis
    Очереди и кэш

MinIO
    Файлы

DeepSeek
    AI анализ
```

Главный принцип архитектуры:

> Пользовательские действия должны быть быстрыми, а тяжёлые процессы должны выполняться асинхронно через очереди.
