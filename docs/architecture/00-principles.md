# Архитектурные принципы проекта "Ревьюша"

## 1. Общие принципы

### 1.1. Проектирование от бизнес-задачи

Каждая техническая реализация должна решать конкретную пользовательскую или бизнес-задачу.

Нельзя добавлять технологии или архитектурные решения без понимания их роли в системе.

Каждая крупная фича должна иметь:

- описание проблемы;
- ожидаемый результат;
- ограничения;
- влияние на существующую систему.

---

### 1.2. Простота важнее сложности

Архитектура должна быть достаточно сложной для решения текущих задач, но не усложняться заранее.

Новые абстракции добавляются только при наличии реальной необходимости.

---

### 1.3. Разделение ответственности

Каждый компонент системы отвечает только за свою область.

Примеры:

- Frontend отвечает за пользовательский интерфейс.
- API отвечает за бизнес-логику.
- Worker отвечает за фоновые задачи.
- PostgreSQL отвечает за постоянное хранение данных.
- Redis отвечает за быстрые временные данные и очереди.
- MinIO отвечает за хранение файлов.

---

# 2. Архитектурные правила

## 2.1. Backend не выполняет долгие операции синхронно

Любая операция, которая может занимать значительное время, должна выполняться асинхронно.

Примеры:

- анализ проекта;
- обработка большого количества файлов;
- запросы к LLM;
- генерация отчётов;
- экспорт данных.

Поток:

Пользователь → API → Queue → Worker → Результат

---

## 2.2. API является единой точкой доступа

Frontend и внешние клиенты не работают напрямую с базами данных или внутренними сервисами.

Все взаимодействия проходят через API.

---

## 2.3. Сервисы должны быть независимыми

Каждое приложение должно иметь возможность:

- запускаться отдельно;
- масштабироваться отдельно;
- обновляться отдельно.

Компоненты системы:

- Web приложение;
- Admin приложение;
- API;
- Worker.

---

## 2.4. Общий код выносится в packages

Код, который используется несколькими приложениями, не копируется.

Примеры:

- TypeScript типы;
- UI компоненты;
- конфигурации;
- утилиты;
- API клиент.

Такой код хранится в shared packages.

---

# 3. Работа с данными

## 3.1. PostgreSQL является источником истины

Все основные данные системы хранятся в PostgreSQL.

Примеры:

- пользователи;
- проекты;
- результаты анализа;
- настройки;
- права доступа.

---

## 3.2. Файлы не хранятся в базе данных

Большие файлы хранятся только в объектном хранилище MinIO.

PostgreSQL хранит только:

- путь;
- метаданные;
- размер;
- тип;
- владельца;
- связь с сущностью.

---

## 3.3. Redis используется только для временных данных

Redis используется для:

- кэширования;
- очередей;
- временных данных;
- блокировок;
- rate limiting.

Критические данные не должны зависеть от Redis.

---

# 4. Работа с AI

## 4.1. LLM не является частью бизнес-логики

Вызовы AI должны идти через отдельный слой.

Бизнес-логика не должна зависеть от конкретной модели.

Например:

Плохо:

```

ReportService → DeepSeek API

```

Хорошо:

```

ReportService
|
|
AI Service
|
|
DeepSeek / другая модель

```

---

## 4.2. AI должен быть заменяемым

Система должна позволять заменить:

- DeepSeek;
- другую LLM;
- локальную модель.

Без переписывания основной логики.

---

## 4.3. Все AI операции должны быть контролируемыми

Необходимо учитывать:

- стоимость запросов;
- размер контекста;
- ошибки модели;
- повторные запросы;
- время выполнения.

---

# 5. Безопасность

## 5.1. Минимальные требования безопасности обязательны

Система должна иметь:

- JWT авторизацию;
- управление ролями;
- проверку входных данных;
- ограничение доступа;
- безопасную работу с файлами.

---

## 5.2. Пользовательские данные изолированы

Пользователь может получать доступ только к своим:

- проектам;
- файлам;
- отчётам;
- настройкам.

---

## 5.3. Все внешние данные считаются недоверенными

Проверяются:

- файлы;
- пользовательский ввод;
- параметры API;
- данные от внешних сервисов.

---

# 6. Качество разработки

## 6.1. Код должен быть поддерживаемым

Проект должен иметь:

- единый стиль кода;
- линтеры;
- форматирование;
- документацию;
- тесты.

---

## 6.2. Изменения проходят проверку

Любая новая функциональность должна проходить:

- проверку типов;
- автоматические тесты;
- code review;
- CI pipeline.

---

## 6.3. Документация является частью разработки

Архитектура, API и важные решения должны документироваться вместе с кодом.

---

# 7. Масштабируемость

## 7.1. Компоненты должны масштабироваться независимо

Например:

При росте количества анализов можно увеличить количество Worker, не увеличивая API.

---

## 7.2. Система должна поддерживать рост

Архитектура должна позволять добавить:

- новые языки программирования;
- новые AI модели;
- Git интеграции;
- командную работу;
- новые типы отчётов.

---

# 8. Принцип разработки проекта

Ревьюша разрабатывается как production-ready SaaS продукт.

Приоритеты:

1. Корректность.
2. Поддерживаемость.
3. Безопасность.
4. Масштабируемость.
5. Скорость разработки.
